Lesson 0038: Error Handling & API Response Standardization

Lahat ng API response mo dapat may iisang format — para predictable ang error handling sa frontend.

Lesson Goal Makagawa ng standardized API response format sa Laravel at mag-implement ng consistent error handling sa Next.js frontend.

Standardized API Response Structure

Ang consistent na response format ay mahalaga para predictable ang behavior ng frontend. Lahat ng API response ay dapat sumunod sa iisang pattern.

// Standard Response Format
{
    "success": true|false,
    "message": "Human-readable message",
    "data": { ... },          // actual data (nullable)
    "errors": { ... },        // validation errors (nullable)
    "meta": {
        "current_page": 1,
        "last_page": 10,
        "per_page": 15,
        "total": 150
    }
}

Laravel API Response Helper

Gumawa ng helper class para sa standardized responses.

// app/Helpers/ApiResponse.php
class ApiResponse
{
    public static function success($data = null,
        string $message = 'Success', int $code = 200)
    {
        return response()->json([
            'success' => true,
            'message' => $message,
            'data'    => $data,
            'errors'  => null,
        ], $code);
    }

    public static function error(string $message = 'Error',
        int $code = 400, $errors = null)
    {
        return response()->json([
            'success' => false,
            'message' => $message,
            'data'    => null,
            'errors'  => $errors,
        ], $code);
    }

    public static function validationError($errors,
        string $message = 'Validation failed')
    {
        return self::error($message, 422, $errors);
    }

    public static function notFound(string $message = 'Resource not found')
    {
        return self::error($message, 404);
    }
}

Frontend Error Handling

Sa Next.js, gumawa ng centralized error handler na gumagamit ng standardized response format.

// lib/error-handler.ts
import { toast } from 'react-hot-toast';

interface ApiError {
  success: boolean;
  message: string;
  errors?: Record<string, string[]>;
}

export function handleApiError(error: any): void {
  if (error.response) {
    const data: ApiError = error.response.data;
    const status = error.response.status;

    switch (status) {
      case 422:
        // Validation errors — inline or modal
        if (data.errors) {
          Object.values(data.errors).forEach((msgs) => {
            toast.error(msgs[0]);
          });
        }
        break;
      case 401:
        toast.error('Please login first');
        // Redirect to login
        break;
      case 403:
        toast.error('You do not have permission');
        break;
      case 404:
        toast.error('Resource not found');
        break;
      default:
        toast.error(data.message || 'Something went wrong');
    }
  } else if (error.request) {
    toast.error('Network error — please check your connection');
  } else {
    toast.error('An unexpected error occurred');
  }
}

Inline vs Toast vs Modal Errors

  • Inline errors — para sa form validation, sa tabi mismo ng input field
  • Toast notifications — para sa general success/error messages
  • Modal errors — para sa critical errors na nangangailangan ng user action
// Inline error example
<div>
  <input name="email" />
  {errors.email && (
    <p className="text-red-500 text-sm">{errors.email[0]}</p>
  )}
</div>
